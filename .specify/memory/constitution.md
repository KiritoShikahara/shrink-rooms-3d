# Shrink Rooms 3D Constitution

## Core Principles

### I. 課題要件の遵守 (NON-NEGOTIABLE)
- UE5.7.4 で新規プロジェクトを作成し、1から制作する。
- ゲームスタート → ゲームオーバー/クリアの流れが分かること。
- 前期システム(扉・鍵・スイッチ・ダメージ/即死・ゴール・UI表示)を含める。
- 出典: `doc/後期課題_要件まとめ.md`

### II. Blueprint 中心・コードも評価対象
- ロジックは Blueprint で実装する(C++ は使わない)。
- BP は評価対象のため、ノードを整理し、コメントと命名規則(BP_/WBP_/IA_/DT_)を守る。
- 共通処理は親BP・コンポーネント・インターフェースで共有する(講義 011/012 の内容)。

### III. 提出可能性 (サイズ・環境互換)
- Git 提出。`.gitignore`(Binaries/Intermediate/Saved/DerivedDataCache 等)必須。
- リポジトリは 2GB 以下。不要なテクスチャ・アセットを入れない。
- 標準・同梱プラグインのみ使用する。確認者の環境で動かないプラグインは禁止。

### IV. グリッド/ターン制の決定性
- 盤面はグリッド、1入力 = 1ターン。壁収縮・敵/ギミック更新はターン終了時に決定的に処理する。
- 同じ入力列は常に同じ結果になること(物理シミュレーション依存のパズル判定は禁止)。

### V. 小さく作り、毎段階で動く
- 1面ずつ完成させる。各段階で PIE により起動からクリアまで通せる状態を保つ。
- 最小の実装で要件を満たし、過剰な機能を足さない。

## 制約
- 対象: Windows / 単一プレイヤー / 5ステージ / トップダウン固定カメラ。
- 手動プレイテストのチェックリストを各ステージに用意する(自動テスト基盤は設けない)。

## 開発フロー
- Spec Kit: specify → clarify → plan → tasks → implement。
- 仕様は `specs/NNN-*/` に置く。変更は仕様を先に更新する。

## Governance
本憲章は他の慣習に優先する。改訂は理由を記録し、バージョンを上げる。
